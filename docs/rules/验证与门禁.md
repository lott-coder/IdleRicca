# 验证与门禁（Unity）

> 源包（Roblox）因"无 CLI 构建链、无单元测试框架"而设计了 Phase 4.5 手动 Play 用例表。
> **Unity 有测试框架，这条必须升级**；同时引入源包 `quality-gate.md` 的 **P0–P3 分级与数值门禁**——只有分级没有数值，门禁就是形容词。
> 本文是验收层的**唯一权威**。`verification-before-completion` 技能只补充"何时调用"，不重复本文表格。

---

## 1. 证据等级（L0–L4）

| 级别 | 证据 | 成本 | 能证明什么 | 不能证明什么 |
|---|---|---|---|---|
| **L0** | 编译通过（0 error） | 秒级 | 语法/类型/引用正确 | 行为正确 |
| **L1** | EditMode 测试通过 | 秒–分钟 | 纯逻辑、数值公式、状态机、存档迁移 | 场景/协程/UI |
| **L2** | PlayMode 测试通过 | 分钟 | 生命周期、协同、输入→表现链路 | 手感、视觉、性能主观感受 |
| **L3** | 手动 Play 观察 | 分钟 | 真实观感、边界情景 | 可重复性（人眼会漏） |
| **L4** | 截图 / 录屏 / Profiler 数据 | 分钟 | 视觉状态、性能数字 | 逻辑正确 |

## 2. 声明 → 所需证据（强制对照表）

| 你要说的话 | 最低证据 | 不够格 |
|---|---|---|
| "编译过了" | L0 | "我看过代码，应该能编" |
| "逻辑改好了" | L1（新增或修改的测试通过） | "代码逻辑是对的" |
| "数值算对了" | L1（表驱动用例：边界/负值/溢出/NaN） | 手动点了几下 |
| "存档不丢数据" | L1（写入→读取→迁移 三段用例） | "我保存过一次" |
| "这个 Bug 修了" | 先复现（红）→ 修 → 同一用例转绿 | "改了这行应该好了" |
| "UI 样式对了" | L4 截图（改前/改后对比） | "样式写对了" |
| "联机同步正常" | L2（两客户端）或 L3 + 日志 | "本地单机测过" |
| "性能没问题" | L4：Profiler 数字 + 帧时间/分配（见 §2.6） | "感觉挺流畅" |
| "分层没破" | G4 asmdef 白名单通过 | "我没引 Presentation" |
| "Phase 完成" | 逐条核对本 Phase 产物 + 验收标准 | 单个用例过了 |
| "可以归档" | L1 全绿 + §3 门禁全部通过 | "审核说没问题" |

**铁律**：**没有新鲜证据，不许宣称完成。** 上一轮通过不算数——代码又改过 = 证据过期。

## 2.5 质量分级 P0–P3（分级决定"能不能放行"）

> 来源：源包 `quality-gate.md` §0。**与审核报告的 blocking/warning/info 是两套刻度**：
> P0–P3 判"问题多严重"，blocking/warning/info 判"这次要不要拦"。映射见 §2.7。

| 级别 | 含义 | 处理要求 |
|---|---|---|
| **P0（阻断）** | 破坏玩法、丢数据、可被利用作弊、崩溃、**验证自洽假象** | 未修复不得合入/发布 |
| **P1（严重）** | 明显影响体验或性能，有绕过方式 | 当前迭代内修复 |
| **P2（一般）** | 可维护性问题 | 排入任务清单 |
| **P3（建议）** | 风格与优化空间 | 鼓励，不强制 |

**P0 的典型形态**（Unity 版）：
- 存档结构变更无迁移 / 载入失败静默用默认值
- `Presentation` 层直接改状态（多写入口）
- 外部输入未净化（NaN/负值/越界）就参与结算
- 测试被修改以"通过"（**验证自洽假象**，最严重）
- 事件只订阅不退订导致泄漏
- `Update` 内分配造成持续 GC

## 2.6 数值门禁（没有数字的门禁不算门禁）

### 2.6.1 运行时指标

| 指标 | 阈值 | 级别 | 采集方式 |
|---|---|---|---|
| 帧时间（中端设备 P95） | ≤ 16.67ms（60 FPS 预算）；持续 > 33ms = P1 | P1 | Profiler / `FrameTimingManager` |
| GC Alloc（每帧稳态） | 目标 0 B；> 1 KB/帧 = P1（热路径） | P1 | Profiler → GC Alloc 列 |
| 峰值内存 | 移动端 ≤ 目标值（按项目定，通常 1.5–2 GB）；超限触发资产瘦身评审 | P2 | Profiler → Memory |
| 加载时间 | 主场景首帧 ≤ 目标值（按项目定）；超限需 loading 态兜底 | P2 | 计时打点 |
| 崩溃率 | > 2% 触发调查 | P0 | 发布后遥测 |
| 包体 | 增量 > 阈值（如 50MB）需评审 | P2 | Build Report |

**结论必须有工具数据**，禁止凭感觉。`Profiler` 的 Editor 数据仅供定位，**真机数据才算数**。

### 2.6.2 性能基准（回归门禁）

| 规则 | 说明 |
|---|---|
| 基准必须可复跑 | 固定负载规模 + 固定 seed + 固定设备档 |
| 判定三态 | `PASS`（相对基线劣化 ≤10%）/ `FAIL`（>10% 且波动 <10%）/ `NOISE`（波动 ≥10%） |
| **NOISE 不是 PASS** | 波动大的项重跑；仍不稳则该负载本身要修 |
| 取中位 | 门禁跑 3 轮取中位，单轮不算 |
| **基线变更需人工确认** | 禁止脚本自动覆写基线（防"温水煮青蛙"式慢性劣化） |
| 改负载/改场景 → 旧基线作废 | 必须重收 |

Unity 侧用 `Unity Performance Testing` 包（`PerformanceTest`/`Measure.Frames()`）承载，不另造框架。

### 2.6.3 安全与数据

- 权威端唯一写入口（见 `架构.md §2`）；表现层不得裁定
- Client 侧提交的数据一律视为可伪造：类型/范围/冷却/权限/距离五项校验缺一即 **P0**
- 存档：schema 版本 + 迁移 + 原子写 + 失败显性（见 `架构.md §5`）

## 2.7 两套刻度的映射

| 审核报告标签 | 对应 P 级 | 放行规则 |
|---|---|---|
| `blocking` | P0 / 关键 P1 | 必须修，不得归档 |
| `warning` | 一般 P1 / P2 | 可延期；单阶段 ≥5 条或跨阶段 ≥10 条 → STOP |
| `info` | P3 | 仅记录 |

> 审核报告仍用 blocking/warning/info（人读友好），**归档门禁同时校验 P0 是否清零**。

## 3. 机器门禁（脱离提示词，由 CI/分析器执行）

IdleRicca 当前使用本机 PowerShell 执行门禁（默认待确认）。在项目根目录运行以下命令。Unity 可执行文件路径随本机安装位置调整。启动批处理前关闭该项目的编辑器窗口。

```powershell
$unityEditor = 'C:\Program Files\Unity\Hub\Editor\2022.3.52f1c1\Editor\Unity.exe'
$unityProject = '"' + (Get-Location).Path + '"'
New-Item -ItemType Directory -Path 'Logs' -Force | Out-Null
```

| # | 门禁 | 命令或当前状态 | 阻断级别 |
|---|---|---|---|
| G1 | 编译 0 error | 执行下方编译命令并检查退出码和日志 | 阻断 |
| G2 | 无新增编译 warning | 查阅 G1 的 `Logs/unity-compile.log`，与最近一次验证的日志比较 | 警告 |
| G3 | EditMode 全绿 | 执行下方 EditMode 命令并检查测试结果 XML | 阻断 |
| G4 | asmdef 白名单 | 初始程序集引用按《工程与资源》§2 核对，自动校验待接入 | 阻断 |
| G5 | 无 Missing Script | 初始场景可在 Unity 中打开核对，批量扫描待接入 | 阻断 |
| G6 | 关键路径 PlayMode | 执行下方 PlayMode 命令并检查测试结果 XML | 阻断（合并前） |
| G7 | 存档 schema 往返 | 随存档功能添加测试用例 | 阻断 |
| G8 | 配置资产校验（ID 唯一/引用非空） | 随配置资产添加校验入口 | 阻断 |

G1 编译命令

```powershell
(Start-Process -FilePath $unityEditor -ArgumentList '-batchmode', '-nographics', '-quit', '-projectPath', $unityProject, '-logFile', 'Logs/unity-compile.log' -WindowStyle Hidden -Wait -PassThru).ExitCode
```

G3 EditMode 和 G6 PlayMode 测试命令

```powershell
(Start-Process -FilePath $unityEditor -ArgumentList '-batchmode', '-nographics', '-projectPath', $unityProject, '-runTests', '-testPlatform', 'EditMode', '-testResults', 'Logs/editmode.xml', '-logFile', 'Logs/unity-editmode.log' -WindowStyle Hidden -Wait -PassThru).ExitCode
(Start-Process -FilePath $unityEditor -ArgumentList '-batchmode', '-projectPath', $unityProject, '-runTests', '-testPlatform', 'PlayMode', '-testResults', 'Logs/playmode.xml', '-logFile', 'Logs/unity-playmode.log' -WindowStyle Hidden -Wait -PassThru).ExitCode
```

> **落地顺序**：G1 → G3 → G4 → G5（一天内可完成），G2/G6/G7/G8 随后。
> 不要一开始追覆盖率——先把"能编译、能测、能查引用、能查配置"这条最小闭环立起来。

## 4. 测试分层（保守版）

| 层 | 测什么 | 用什么 | 占比 |
|---|---|---|---|
| Domain | 公式、状态机、边界 | 纯 NUnit `[Test]`，无 Unity 环境 | 70% |
| Application | 用例编排、事务、幂等 | NUnit + 内存替身（fake store） | 25% |
| Presentation | 关键交互链路 | `[UnityTest]` PlayMode，**只测关键路径** | 5% |

**为什么 EditMode 为主**：PlayMode 慢、易 flaky、需要真实场景与渲染环境。把逻辑挤到 Domain/Application，就能用最便宜的方式覆盖最多行为——这也是架构分层的直接收益。

### 测试 asmdef 要求

`Game.Tests.EditMode.asmdef` 必须：

```json
{
  "name": "Game.Tests.EditMode",
  "references": ["Game.Domain", "Game.Application", "UnityEngine.TestRunner", "UnityEditor.TestRunner"],
  "includePlatforms": ["Editor"],
  "precompiledReferences": ["nunit.framework.dll"],
  "defineConstraints": ["UNITY_INCLUDE_TESTS"]
}
```

> 漏了 `UnityEngine.TestRunner` 或 `UNITY_INCLUDE_TESTS`，Test Runner 会发现不到测试——这是最常见的"测试写了但没跑"的原因。

## 5. 验收标准怎么写（Phase 1/3 强制格式）

❌ 不合格：
> 实现商店购买功能，体验流畅。

✅ 合格：

| # | 验收项 | 证据级别 | 具体判据 |
|---|---|---|---|
| AC-1 | 余额足够时购买成功 | L1 | `TryBuy` 返回 `Ok`；`Coins` 减少 `price`；背包 +1 |
| AC-2 | 余额不足时整体拒绝 | L1 | 返回 `Fail("INSUFFICIENT")`；`Coins` 与背包**均不变** |
| AC-3 | 重复请求幂等 | L1 | 同 `requestId` 连发 2 次，只发货 1 次 |
| AC-4 | 数值脏数据不崩 | L1 | 传入 `NaN`/`-1`/`long.MaxValue` 时拒绝且状态不变 |
| AC-5 | 按钮置灰与提示 | L4 | 截图：余额不足时按钮灰、显示差额 |

**每条 AC 必须能被 §1 的某一级证据验证**，否则这条 AC 是装饰。

## 6. 手动验证（保留，但降级）

Unity 里仍需手测：

| 场景 | 为何不能自动 |
|---|---|
| 手感、镜头、打击感 | 主观体验，无客观断言 |
| 分辨率/宽高比适配 | 需真实设备或多种比例 |
| 长时间运行的泄漏 | 需长跑，CI 成本高 |
| 平台相关（手柄/触屏/主机） | 需真机 |

**要求**：手测必须留 **L4 证据（截图/录屏）+ 一句"我看到了什么"**，写进 `05-issues.md` 的验证表。禁止只写"Play 验证通过"。

---

## 7. 调试纪律

| 阶段 | 动作 |
|---|---|
| 1. 复现 | 写一个**能稳定变红**的测试或用例；不能复现就先不加修复 |
| 2. 定位 | 二分（注释/回滚）/ 加日志 / 断点；**先证伪假设，不要先改代码** |
| 3. 修复 | 改最小面；同时补一条防止回归的测试 |
| 4. 验证 | 红 → 绿；再跑一遍相邻用例（防连带破坏） |

**禁止**：改代码"试试看"、加了日志就宣称定位、修复后不补回归测试。

## 8. 反模式

| 反模式 | 后果 |
|---|---|
| 用"逻辑上应该对"替代测试 | 未验证的东西被固化成 `spec/` 真相 |
| 只测 happy path | 边界与脏数据引发线上事故 |
| PlayMode 覆盖一切 | 测试慢到没人跑，最终全部失效 |
| 手测不截图 | 无法回溯"当时到底看到什么" |
| 测试依赖真实网络/真实存档 | flaky，最终被忽略 |
| 为过测试改测试 | 门禁形同虚设（**P0 验证自洽假象**） |
| 只写"性能 OK"不给数字 | 无法判断劣化 |

## 9. UI 验收（清单式双闸门）

> 迁移自源包 `roblox-ui-design` 的"构建者机检 + 独立审查员"双闸门**思想**（其 17 项审计是 Roblox GUI 专属，不可照搬）。
> Unity/UE 的 UI 是代码驱动（UI Toolkit / UMG），所以门禁改为**同一份清单、两个角色**：

| 角色 | 做什么 | 不能做什么 |
|---|---|---|
| **构建者**（写 UI 的人/agent） | 交付前**逐条自查**本清单，把结果写进 `05-issues.md` | 不能给自己判"通过" |
| **独立审查员**（不参与构建的 agent/人） | 用**同一份清单**复核，重点看构建者**没提到**的项 | 不能边审边改（只报告） |

**清单（每条给证据）**：

| # | 检查 | 证据 |
|---|---|---|
| U1 | 布局：主流分辨率（如 1280×720 / 1920×1080 / 2560×1440）下不错位、不溢出 | 截图 ×2 以上 |
| U2 | 安全区：刘海/圆角/手柄安全边距不遮挡内容 | 截图或配置说明 |
| U3 | 四态齐全：空 / 加载 / 正常 / 错误（含禁用态） | 截图或状态表 |
| U4 | 异步等待有**超时**与失败提示（禁止无限转圈） | 代码位置 + 截图 |
| U5 | 可点区域 ≥ 44×44 px（触屏）/ 手柄可达 | 数值或截图 |
| U6 | 点击有即时反馈（<100ms），长操作有 loading | 录屏 |
| U7 | 文案走本地化表，无硬编码字符串 | grep 证据 |
| U8 | 层级/遮挡正确（弹窗盖住背景、不吞点击） | 截图 |
| U9 | 无每帧重排/重绘热点（布局重建、字符串拼接） | Profiler 截图 |
| U10 | 退出/关闭路径明确（含返回键、ESC、手柄 B） | 操作步骤 |

**放行规则**：U1–U4 任一未过 = 阻断（对应 P1）；其余未过 = 记录后可交付。
**审查员交付物**：`04-review-report.md` 追加一节「UI 审查」，逐项写 通过/未过 + 证据。

> 现状：**没有自动化结构审计脚本**（源包那套 17 项依赖 Roblox GUI 属性）。本清单是人工/截图级门禁，不要假装成机检。
