# 工程与资源（Unity）

> 目标：让"代码—资产—依赖"三者的变更都可追踪、可审查、可回滚。这是 Roblox 版 `05-资源与rbxl协调.md` + `Rojo与Wally适配.md` 的对应物，但**问题形态不同**。

---

## 1. 目录结构

```
project/
├─ Assets/
│  ├─ Scripts/
│  │  ├─ Domain/            Game.Domain.asmdef
│  │  ├─ Application/       Game.Application.asmdef
│  │  ├─ Infrastructure/    Game.Infrastructure.asmdef
│  │  └─ Presentation/      Game.Presentation.asmdef
│  ├─ Tests/
│  │  ├─ EditMode/          Game.Tests.EditMode.asmdef
│  │  └─ PlayMode/          Game.Tests.PlayMode.asmdef
│  ├─ Config/               ScriptableObject 资产
│  ├─ Art/                  模型/贴图/材质
│  ├─ Prefabs/
│  ├─ Scenes/
│  └─ Settings/
├─ Packages/
│  ├─ manifest.json         ← 依赖声明（入库）
│  └─ packages-lock.json    ← 锁版本（入库）
├─ ProjectSettings/         ← 入库
└─ docs/                    ← 本工具链落位处（见 README）
```

**不入库**：`Library/`、`Temp/`、`Obj/`、`Logs/`、`UserSettings/`、`Build/`、`*.csproj`、`*.sln`（由 Unity 生成）。

## 2. asmdef 依赖方向（可机检）

```
Presentation ──▶ Application ──▶ Domain
      │                ▲
      └──▶ Domain      │
Infrastructure ─────────┘
```

**白名单**（CI 校验用，写进 `Tools/check-asmdef.ps1` 或 `-executeMethod`）：

| asmdef | 允许 references |
|---|---|
| `Game.Domain` | （空） |
| `Game.Application` | `Game.Domain` |
| `Game.Infrastructure` | `Game.Domain`、`Game.Application` |
| `Game.Presentation` | `Game.Domain`、`Game.Application`、`UnityEngine.UI`、`Unity.TextMeshPro` |

**禁止**：`Game.Domain` 引用 `UnityEngine`（理想态）；若必须引用（如 `Vector3`），在架构文档里显式登记例外并说明原因。

> 这是本工具链在 Unity 上**唯一不依赖 AI 自觉**的架构约束——务必在项目初始化第一天就建好。

## 3. 资源引用

| 规则 | 说明 |
|---|---|
| **直接序列化引用优先** | `[SerializeField] private ItemConfig _config;` — 引用可见、可校验、重命名自动跟随 GUID |
| **禁止字符串路径查找** | `Resources.Load("Prefabs/Item")` / `GameObject.Find("Hud/Button")` 一律禁止 |
| **跨场景引用** | 用 `ScriptableObject` 事件通道或启动期注入，禁止跨场景拖引用 |
| **Addressables** | 首版不引入；有包体/热更需求时再评估（见架构 §8） |

### 与 Roblox 版的根本差异

源包有一条铁律："**代码改实例名 → 必须在 Studio 同步改名**"，因为 Roblox 用字符串引用且 Script Sync 不同步结构。**Unity 里这条不成立**：引用是 `{fileID, guid}`，重命名会自动跟随。

**但故障面换了个形状**，必须替换成新规则：

| 新风险 | 症状 | 防线 |
|---|---|---|
| **Missing Script** | `m_Script: {fileID: 0}`，组件变 "Missing" | 删除脚本前先查引用；CI 扫描 prefab/scene 中的 `fileID: 0` |
| **GUID 断裂** | 在 Unity 外部（资源管理器/git）移动或复制资源，未带 `.meta` | **所有资源操作必须在 Unity Editor 内做**；`.meta` 必须入库 |
| **Prefab Override 冲突** | 场景里改了 prefab 实例，prefab 又改了 | 改公共属性走 prefab；实例差异要能解释 |
| **场景 YAML 合并冲突** | 两人改同一场景 | **同一场景同时只允许一人编辑**（写进团队约定） |
| **写死 `/Game/` 路径**（若用 Addressables） | 重命名后静默加载失败 | 禁写死路径；改名后跑一次校验 |

## 4. 版本控制设置（一次配好，终身受益）

`ProjectSettings/EditorSettings.asset` 必须：

```yaml
m_SerializationMode: 2          # Force Text
m_LineEndingsForNewScripts: 1   # Unix（与 .gitattributes 一致）
m_Mode: 1                       # Visible Meta Files
m_AssetPipelineMode: 1
```

`.gitattributes` 建议：

```
* text=auto
*.cs text eol=lf
*.json text eol=lf
*.meta text eol=lf
*.unity linguist-detectable=false
*.prefab linguist-detectable=false
*.asset merge=unityyamlmerge eol=lf
*.unity merge=unityyamlmerge eol=lf
*.prefab merge=unityyamlmerge eol=lf
```

> `unityyamlmerge` 能做**语义合并**，但**解决不了引用冲突**（两边都改了同一个 guid 字段时仍需人工裁决）。所以它降低冲突频率，不消除编辑纪律。

## 5. 依赖管理（UPM）

| 规则 | 说明 |
|---|---|
| `Packages/manifest.json` 入库 | 依赖声明是工程的一部分 |
| `packages-lock.json` **必须入库** | 没有它，CI 与本地会解析出不同版本 |
| 版本**锁定精确号** | `"com.unity.test-framework": "1.4.5"`，不用 `"1.4.x"` |
| Git 依赖必须带 tag + `?path=` | `"https://github.com/org/repo.git?path=/src/Pkg#v1.2.3"` |
| 私有源用 scoped registry | 写进 `manifest.json` 的 `scopedRegistries` |
| OpenUPM / NuGetForUnity | 引入前评估：是否与 `netstandard2.1` 兼容、是否会与 asmdef 循环引用 |

**【禁止】**直接改 `Library/PackageCache/`（会被还原覆盖）；把 `.dll` 手工丢进 `Assets/Plugins` 而不记录来源与版本。

## 6. 配置资产（ScriptableObject）纪律

| 规则 | 说明 |
|---|---|
| 配置只读 | `ScriptableObject` 存策划数据，**运行时不得写回**（会污染资产、进 git diff） |
| 必须有校验 | `OnValidate()` 里检查：ID 非空、数值范围、引用非空 |
| ID 唯一性 | 编辑器脚本批量校验所有配置资产的 ID 冲突 |
| schema 版本 | 配置结构变更时，加迁移或重新生成，不靠"默认值兜底" |
| 数值来源可溯 | 每个调参字段的注释写明来源（策划表 / 公式 / R{n}） |

> 这是相对 Roblox 版的**净收益**：源包用"活表 + 字符串 ID + 运行时校验"，Unity 可以在**编辑期**就把错误挡住。

## 6.5 空配置与缺失资产的可加载性（三范式）

> 来源：源包 `安全隔离与空配置可加载性.md` 的实证契约。**配置表为空、资产未配、字段缺失时，工程必须能启动且不报错**——否则策划一新建空表就让游戏起不来。

| 场景 | 错误做法 | 正确做法 |
|---|---|---|
| 配置资产未赋值（null） | 直接访问 → `NullReferenceException` | 加载处做 **null 兜底**（用默认配置或安全默认值），并在日志中 `Warn` 一次 |
| 配置集合为空 | 遍历时假设至少一项 | 遍历 + **存在性判断**；空集合视为"该功能未开启"，不报错 |
| 可选子配置/子资产缺失 | 阻塞式等待或抛异常 | **非阻塞查找**（`TryGet` 语义），缺失即跳过 |

**边界规则（关键）**：只有"**字段为 null / 空字符串**"才允许静默；一旦**填了值但填错**（格式错、ID 不存在、引用为空资源），必须**报错**。
理由：静默会掩盖配置错误；而对"未填"报错会让空表无法启动。二者的区别是"有没有意图"。

**检测手段**：G8 配置资产校验（ID 唯一、引用非空）只查"填了的值"，不要求"必须填"。

## 7. 构建与 CI（保守版）

| 环节 | 命令/方式 | 频率 |
|---|---|---|
| 编译检查 | `Unity -quit -batchmode -projectPath <p> -logFile -` | 每次提交 |
| EditMode 测试 | `-runTests -testPlatform EditMode -testResults results.xml` | 每次提交 |
| PlayMode 测试 | `-runTests -testPlatform PlayMode` | 合并前 / 夜间 |
| asmdef 白名单校验 | 自定义 `-executeMethod` | 每次提交 |
| Missing Script 扫描 | 自定义 `-executeMethod` 遍历 prefab/scene | 每次提交 |

**【暂不引入】**完整 CD（自动出包/热更/多渠道）。理由：先保证"能编译、能测、能查引用"，出包频率上来再说。

## 8. 反模式

| 反模式 | 后果 | 正解 |
|---|---|---|
| 所有代码一个 asmdef | 分层失效，全量重编译 | 四层拆分 |
| 用 `Resources/` 做大资源管理 | 全量打进包体、按名加载不可查 | 序列化引用 / Addressables |
| 场景里堆业务逻辑 | 无法 diff、无法测试 | 逻辑进 `Application`/`Domain` |
| 在 prefab 上挂配置数据 | 同一 prefab 多实例共享可变状态 | 配置进 `ScriptableObject` |
| 直接改他人场景 | 必然冲突 | 场景独占 + 用 prefab 组合 |
| 忽略 `.meta` 变更 | GUID 漂移、引用断裂 | `.meta` 与资源一起提交 |
