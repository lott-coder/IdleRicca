# 架构（Unity · 保守版 v0.1）

> **本文的边界**：只写"已确认能在 Unity 2022 LTS / Unity 6 上落地"的做法。
> 标注 **【暂不采用】** 的条目是**刻意排除**，不是遗漏——它们要么把边界变成运行时协商（无法静态审查），要么引入当前不需要的运维成本。
> 变更本文需走 `/workflow`（改架构 = 改所有后续迭代的前提）。

---

## 1. 分层：四层，用程序集边界强制

Knit 的 Service / Controller / Shared 三层在 Unity 里**语义可用，命名不可用**——Unity 生态里 "Controller" 已有强语义（MVC、CharacterController），沿用会持续误解。

| 层 | 程序集（asmdef） | 职责 | 允许依赖 | 禁止 |
|---|---|---|---|---|
| **Domain** | `Game.Domain` | 纯 C# 模型、数值公式、状态机、规则 | 无（理想情况下不引用 `UnityEngine`） | 访问场景对象、IO、网络 |
| **Application** | `Game.Application` | 用例编排、**唯一写入口**、会话状态 | Domain | 引用 `MonoBehaviour`、直接读输入 |
| **Infrastructure** | `Game.Infrastructure` | 存档、网络、平台、资源加载 | Domain、Application | 承载业务规则 |
| **Presentation** | `Game.Presentation` | `MonoBehaviour`、UI Toolkit、VFX、输入 | Application、Domain（只读） | **直接改 Domain 状态** |

**映射关系**（便于对照 Roblox 版理解）：

| 源包（Roblox/Knit） | 本文（Unity） |
|---|---|
| Service（服务端权威） | **Application**（写入口）+ **Domain**（规则） |
| Controller（仅表现） | **Presentation** |
| Shared Config（纯数据表） | **ScriptableObject**（数据资产，见 §5） |

### 为什么用 asmdef 而不是"靠自觉"

`asmdef` 的引用是**编译期硬约束**：`Game.Domain` 的 `references` 里没有 `Game.Presentation`，就永远不可能反向依赖。这是本方法论在 Unity 上**唯一真正可强制的分层**——比代码审查可靠，也比注释可靠。

**检测手段**：CI 里跑一次 `-executeMethod` 校验各 asmdef 的 `references` 白名单（见 [工程与资源.md](工程与资源.md) §2）。

## 2. 权威模型：只有两种，且必须在架构文档里显式声明

Roblox 的客户端**物理上**无法修改服务端状态，所以"服务端权威"是陈述句。Unity 不是——同一个 `NetworkBehaviour` 既可能跑在服务端也可能跑在客户端，权威来自运行时判断。

**因此本规范要求：项目必须在架构层先声明唯一一种权威模式，不允许混用。**

IdleRicca 暂用 **A. 本地权威（单机，默认待确认）**，由 `Application` 层负责状态写入。

| 模式 | 适用 | 权威位置 | 必须的校验点 |
|---|---|---|---|
| **A. 本地权威**（单机/离线） | 单机、原型、纯 PvE | `Application` 层唯一写入口 | 输入净化（NaN/越界/类型）+ 状态守卫 + 幂等标记 |
| **B. 专用服务器权威** | 联机对战、含交易 | 服务器侧 `Application` 层 | ServerRpc 内做**类型/范围/冷却/权限/距离**五项校验；客户端只发意图 |

**【暂不采用】**

| 项 | 为何排除 |
|---|---|
| Client-host（Host 即玩家） | Host 是玩家 → 权威边界随对局变化，无法静态审查，也无法在 CI 里验证 |
| Distributed authority（NGO 2.x） | 同上，且把"谁能改"变成运行时协商 |
| 客户端预测 + 回滚 | 需要确定性模拟与网络抖动建模，属于"有明确需求后再做"的复杂度 |

> **保守版的代价与收益**：放弃 Host 模式会牺牲"一键联机"的便利；收益是**"服务端权威"重新变成可审查、可测试的事实**——这正是这套方法论赖以成立的前提（见 [验证与门禁.md](验证与门禁.md)）。

**检测手段**：`Application` 层的写方法全部 `internal` + `InternalsVisibleTo` 仅对测试开放；`Presentation` 层对 `Application` 只暴露 `Query` / `Command` 两类接口。

## 3. 通信：三条通道，按"是否跨进程"分流

| 通道 | 机制 | 占比 | 约束 |
|---|---|---|---|
| **进程内** | C# `event` / 接口调用 / 直接方法调用 | ~90% | 默认选它。事件必须可退订 |
| **跨网络** | NGO `[Rpc(SendTo.Server)]` + `NetworkVariable<T>` | ~10%（仅联机） | 逻辑**不得**写在 RPC 里，RPC 只做薄入口转发到 `Application` |
| **跨模块广播** | 显式事件聚合器（一个类，注册/注销成对） | 少量 | 禁止字符串事件名 + 反射 |

**【暂不采用】** 第三方网络库、消息队列、ECS 网络同步。理由：每条通道都增加"状态可能在哪"的搜索空间，而本方法论的核心成本就是**定位状态**。

### RPC 的唯一正确形状

```
客户端：RequestBuy(itemId)  →  RPC  →  服务端：校验(itemId) → Application.Buy(...) → 复制结果
```

❌ 错误：RPC 方法里写结算逻辑（无法单测、无法复用、客户端与服务端逻辑分叉）
✅ 正确：RPC 只做"解包 + 校验 + 转发"，结算在 `Application`，结果通过状态复制或回调事件回传

## 4. 生命周期：两阶段启动（替代 BeforeLoad/AfterLoad）

Roblox 版用 `player:GetAttribute("Loaded")` 做关卡，解决"UI 先于数据就绪"的竞态。Unity 的同类问题是**场景加载与数据加载的时序**。

```
阶段 1  Bootstrapping（无场景依赖）
  ├─ 加载配置（ScriptableObject）
  ├─ 初始化 Application 层服务
  └─ 注册跨模块事件

关卡   Ready 信号（数据/会话就绪）

阶段 2  Presentation
  ├─ UI 绑定（此时数据一定存在）
  └─ VFX / 音频 / 场景表现
```

**硬规则**：
- `Presentation` 层**不得**在 `Awake`/`Start` 里直接读取可能未就绪的数据 —— 必须订阅 `Ready` 或使用 `Awaitable`
- 等待必须有超时（对应源包"`repeat task.wait() until` 无超时"这个真实 Bug）
- `Bootstrapping` 阶段不得依赖任何场景对象

**检测手段**：`Presentation` 层禁止出现 `FindObjectOfType` / `GameObject.Find`（Roslyn 分析器规则，见 §7）。

## 5. 数据：整块快照 + schema 版本（保守到不依赖任何云服务）

Roblox 版的核心教训是"**部分更新会导致静默丢字段**"（客户端做浅替换）。这条在 Unity 里**同样成立**，只是载体从 ProfileService 换成本地存盘。

**保守版存储**：本地 JSON + schema 版本 + 原子写 + 备份槽。

| 规则 | 说明 |
|---|---|
| **整块快照** | 更新某分区时发送/写入**整个分区**，接收侧做整分区替换，不做字段级合并 |
| **schema 版本** | 存档根节点必须有 `schemaVersion`；读取时按版本迁移，缺失字段按模板补全 |
| **原子写** | 写临时文件 → `File.Replace`（或 rename）→ 保留上一版为 `.bak` |
| **失败即显性** | 载入失败必须报错并阻断进入游戏，**禁止静默用默认值开局**（等于覆盖玩家存档） |
| **幂等标记** | 一次性奖励/首登发放必须有布尔或计数标记 |

**【暂不采用】** Unity Cloud Save / PlayFab / 自建后端 —— 直到出现"跨设备"或"联机结算"需求。理由：云端存储引入写锁与冲突语义，在没有并发写入者之前是纯成本。

> 迁移到云端时**不需要改架构**：`Infrastructure` 层换实现即可，因为"整块快照 + 版本 + 幂等"三条语义在两种载体上都成立。

**检测手段**：`Application` 层的 `Save()` 界面只有"整分区提交"一个方法签名，不提供字段级 setter。

## 6. 模块划分：按业务域，不按技术层

✅ 按业务域：`Inventory`（库存：获得/消耗/上限）、`Shop`（购买/发货/退款）、`Progression`（经验/等级）
❌ 按技术层：`SaveService`、`NetworkService`、`AudioManager`（后者只能是工具，不能是业务模块）

| 判断 | 结论 |
|---|---|
| 能用一句话讲清"负责游戏的哪一块" | 是业务模块 |
| 只能讲清"它是个工具" | 是 `Utility` 或 `Infrastructure` |
| 两个模块频繁互调 | 边界划错，合并或重切 |
| 单文件 > ~500 行且有多个独立子主题 | 拆成目录 + 子模块 |
| 起步就建 20 个空模块 | 过度设计，先 3–5 个 |

**模块分类表（IdleRicca 初始配置，默认待确认）**：

| 模块 | 范围 |
|---|---|
| `core` | 启动、生命周期、领域基础类型 |
| `gameplay` | 玩家操控、第三人称镜头、战斗与伤害 |
| `data` | 存档、schema 迁移、配置加载 |
| `economy` | 货币、价格、结算、账本 |
| `progression` | 经验、等级、解锁 |
| `ui` | 界面、HUD、弹窗 |
| `audio` | BGM/SFX |
| `_misc` | 无法归类的 |

> `/workflow init` 时若模块名不在上表，**先改这张表**再初始化——模块分类是文档归类的根，事后改会留下孤儿目录。

## 7. 可验证性声明：每条架构约束必须有检测手段

这是本规范与"架构散文"的分界线。**写进文档但无法检测的约束，一律降级为建议。**

| # | 约束 | 检测手段 | 级别 |
|---|---|---|---|
| C1 | Domain 不依赖 UnityEngine | asmdef 引用白名单 + CI 校验 | 阻断 |
| C2 | Presentation 不改 Domain 状态 | 分析器：`Presentation` 层内禁止出现 `Domain` 的 setter 调用 | 阻断 |
| C3 | 禁 `GameObject.Find` / `FindObjectOfType` | Roslyn 分析器（`UNT*` 或自定义规则） | 阻断 |
| C4 | 禁 public 字段序列化 | 分析器：`public` 字段 + `[SerializeField]` 缺失 | 警告 |
| C5 | 事件订阅成对 | 分析器：`+=` 无对应 `-=`（同类型内） | 警告 |
| C6 | 存档整块提交 | `Application` 层 API 形状审查 | 警告 |
| C7 | 等待有超时 | 分析器：`while(...)` 轮询无 timeout 常量 | 警告 |

> 落地顺序：先 C1（asmdef，零成本）→ 再 C3/C4（现成分析器）→ 最后自定义规则。**不要一开始就写全套分析器。**

## 8. 保守边界总表（迁移决策留痕）

| 项 | 采用 | 暂不采用 | 理由 |
|---|---|---|---|
| 分层 | 四层 asmdef | ECS/DOTS 架构 | DOTS 的心智模型与"读文档即可定位状态"冲突 |
| 权威 | 本地 / 专用服务器 | Client-host、分布式权威、预测回滚 | 权威边界须可静态确认 |
| DI | 构造注入（VContainer 或手写组合根） | 反射式全局 Service Locator | 后者让依赖不可见，审查失效 |
| 配置 | ScriptableObject | CSV 运行时热更 | 先要编译期校验 |
| 存档 | 本地 JSON + 版本 | 云存档/后端 | 无并发写入者前是纯成本 |
| 网络 | NGO（若需联机） | 第三方网络库 | 减少状态搜索空间 |
| 测试 | EditMode 为主 + 关键路径 PlayMode | 全量 PlayMode 覆盖 | PlayMode 慢且易 flaky |
| 资源 | 直接序列化引用 | Addressables（首版） | 引用可见性优先；有包体/热更需求再上 |

> 表中每一项都可单独升级，且**升级不改变流程**——这是保守版的真正价值：**先让流程跑起来，再让架构长大**。
