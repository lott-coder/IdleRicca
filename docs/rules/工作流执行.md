# 工作流执行（Phase 0–5 · 阶段门禁）

> 本文定义 `/workflow plan` 的各阶段规则和所有项目改动的归档要求。**核心机制与引擎无关**。
> 检查项来源：架构 → [架构.md](架构.md)；编码 → [编码约定.md](编码约定.md)；证据 → [验证与门禁.md](验证与门禁.md)。

版本：v1.1.0（Unity 移植版）｜更新：2026-11-22

---

## 快速开始

```
/workflow init minor economy purchase        # 初始化迭代（模块 / 子分类）
/workflow plan --prd docs/prd.png            # 带 PRD（Phase 0 解析）
/workflow plan                               # 默认 brainstorm 交互模式
/workflow plan --direct                      # 快速模式（直接写文档）
/workflow plan --unattended                  # 无人值守（自动决策，见无人值守安全.md）
/workflow verify design                      # 手动触发审核
/workflow status                             # 查询状态
/workflow archive purchase                   # 归档（delta 合并进 spec/）
```

---

## 执行红线（严格禁止）

阶段审核与确认适用于完整工作流。归档、规格增量、活规格写入和验证证据要求适用于所有项目改动。

- ❌ **禁止跳过审核**：每个阶段完成后必须调用 `plan-reviewer` / `code-reviewer`
- ❌ **禁止审核后直接进下一阶段**：必须先 按《AI 协作纪律》用宿主提问工具展示结果并等待确认
- ❌ **禁止批量询问**：一次只过一个阶段
- ❌ **禁止先做后补文档**：规划必须先落到 `change/{module}/_tmp/`
- ❌ **禁止忽略阻断项**：有阻断不得进入下一阶段
- ❌ **禁止跳过归档**：所有项目改动均须在交付完成前用归档工具落盘。归档要求也适用于未启动 `workflow` 的任务。
- ❌ **禁止行为变更无 delta 归档**：涉及可观察行为/契约变更时，`07-spec-delta.md` 必须存在
- ❌ **禁止 delta 校验不过就归档**：`/workflow validate` 失败则阻断
- ❌ **禁止手改 `spec/{module}.md`**：活规格唯一入口是 `archive` 的 delta 合并
- ❌ **禁止跳过验证证据**：任何"完成/修好"声明必须有 [验证与门禁.md](验证与门禁.md) §2 规定的证据
- ❌ **禁止自行假设**：任何疑问必须问用户

### `--unattended` 例外

自治模式下，"审核后询问用户"被**严重度矩阵自动决策**替代，但**审核本身不跳过**。详见 [无人值守安全.md](无人值守安全.md)。

## 未启动 workflow 的归档

直接实现、Bug 修复、资产导入、配置调整和文档更新，只要形成持久的项目文件改动，就要归档。只读排查、答疑和只生成验证日志的任务无需新建归档。

1. 按变更归属选定模块、子分类和版本。在 `05-issues.md` 记录改动原因、涉及文件和验收结果，在 `06-knowledge-update.md` 记录知识更新或无需沉淀的依据。其他阶段文档按实际执行的流程留存。
2. 涉及新增或变更活规格契约时准备 `07-spec-delta.md`。已有基线且只恢复既有约定时，按无规格增量归档，在校验和归档命令中使用 `--no-delta`。
3. 执行适用的验证，使用归档工具先预览再正式归档。复核归档目录与版本索引，在交付结果中提供归档路径。归档暂时受阻时，记录具体原因并保留待归档状态。
4. 同一模块的 `_tmp/` 已用于另一迭代时，使用独立项目根准备并验证本次档案。发布时在归档锁下登记本次子分类，保留已有迭代的文档、状态和当前子分类。涉及规格变更时，按项目最新规格和在途契约重新校验后由工具合并。

## Phase 0：需求文档解析（可选）

**触发**：`--prd <路径>`，或对话中直接给了 PRD/截图/PDF。

1. 调用 `prd-reader` 子代理，产出 `change/{module}/_tmp/00-prd-analysis.md`
2. 该文档必须标注：功能需求（FR-xx）、**每条的层归属**（Domain / Application / Presentation）、依赖的资产或配置
3. 主会话读该文档作为 Phase 1 输入
4. 自动进入 Phase 1

---

## Phase 1：需求分析

**默认（brainstorm-design）**：
1. 探索上下文：相关代码、`knowledge/{module}.md`、`change/{module}/` 历史
2. **在途契约软检查**：读 `change/versions.json` 找出其它 `status=wip` 模块，汇总其在途的接口/数据/资产契约 → 作为需求澄清输入（不阻断）
3. 逐轮澄清（**一次一问**，优先选择题）：核心目标 / 玩法机制 / 目标用户 / 成功标准 / 约束 / 引擎特有维度
4. 提出 2–3 个方向方案（精简 / 标准 / 旗舰）
5. 分块展示 → 每块分别向用户确认
6. 写 `01-requirements.md` → 最终审查
7. `plan-reviewer` 审核 → 写 `04-review-report.md`
7.5 （可选，建议必做）调 `experience-designer` 从留存/变现视角评审 → 意见追加到同一报告；它**不阻断流程**，但"这需求不值得做"的结论必须原样上报
8. 展示 + 按答复整理 → 用户确认 → Phase 2

**`--direct`**：跳过问答，直接写 `01-requirements.md`；审核流程一致。

**本阶段检查项（引擎特化）**：
- 每条需求是否标注了层归属（Domain/Application/Presentation）？
- 是否识别了权威模式（本地 / 专用服务器）？
- 是否识别了需要新增/修改的配置资产（ScriptableObject）？
- 验收标准是否按 [验证与门禁.md](验证与门禁.md) §5 的表格格式写？（含证据级别列）

**产出**：`01-requirements.md`

---

## Phase 2：系统设计

**默认（brainstorm-develop）**：
1. 深入代码：定位相关 asmdef/类、现有模块边界、`knowledge/{module}.md`
2. 逐轮澄清技术维度（**一次一问**）：架构落位 / 数据结构 / 交互流程 / 性能 / 兼容性 / 复杂度
3. 提出 2–3 个技术方案（含分层落位、数据流、关键类型清单、性能策略、实现步骤、风险）
4. 分块展示（架构 → 数据结构 → 交互 → 防御）→ 每块确认
5. 写 `02-design.md`（**核心重点前置** + 后补伪代码）
6. **产出 `07-spec-delta.md`**（涉及行为变更时）：
   - ADDED / MODIFIED / REMOVED 三段
   - MODIFIED/REMOVED 引用现存 `R{n}`；ADDED 用新 `R{n}`
   - 每条至少一个「**当…则…**」场景，且"则"落在**权威端**（联机=服务端；单机=Application 唯一写入口）
   - **在途契约终检**：比对 C1–C5 冲突表（见下），0 冲突则在 `02-design.md` 头部记一行
6.5 （可选）调 `unity-systems-engineer` 评估分层落位、可测性与性能风险 → 结论并入 `02-design.md` 的「架构约束遵守声明」
7. `plan-reviewer` 审核 → 追加 `04-review-report.md` → 展示 → 确认
8. 用户确认 → Phase 3

### 共享契约冲突表（C1–C5）

| # | 共享契约 | 冲突形态 | Unity 载体 |
|---|---|---|---|
| C1 | 公开接口 / 事件名 | 同名互覆盖、监听错事件 | `Application` 层接口 + `event` 签名 |
| C2 | 存档分区字段 | 两个系统写同一分区，互相冲掉 | `SaveData` 的分区键 |
| C3 | 配置资产结构 | 同资产加字段，对方读取崩 | `ScriptableObject` 字段与 `OnValidate` |
| C4 | 序列化引用 / GUID | 资源重命名/移动导致引用失效 | prefab/scene 的 `{fileID,guid}` |
| C5 | 共享服务接口 | 改签名/返回结构，调用方断 | `Application` 层公开方法 |

**比对范围**：本模块 `02-design.md` 的接口清单 + 数据流 + 资产依赖，逐项比对其它 wip 模块同类章节及其 `07-spec-delta.md`。

**产出**：`02-design.md`、`07-spec-delta.md`

---

## Phase 3：计划制定

1. 确认接口约束（方法签名、事件名、存档字段）
2. 写 `03-plan.md`：任务清单、依赖、回滚方案
3. **每项任务必须标注**：
   - 输出文件路径（`Assets/Scripts/Application/Shop/ShopService.cs`）
   - 层归属
   - 需要的测试（L1/L2）
   - 是否涉及资产修改（prefab/scene/ScriptableObject）——**涉及则单列一节**
4. `plan-reviewer` 审核（最多 3 轮修复）
5. 追加 `04-review-report.md`
6. 生成执行摘要
7. 展示摘要 → 用户确认 → Phase 4

**产出**：`03-plan.md`

---

## Phase 4：代码执行

1. 按 `03-plan.md` 逐项执行，每完成一项更新状态
2. 遇阻记录到 `05-issues.md`
3. **先写测试再写实现**（至少对 Domain/Application 层的行为）
4. 完成后调用 `code-reviewer` 审查变更
5. 展示审查结果 → 用户确认 → 按答复整理报告
6. 修复审查发现 → 重跑门禁（[验证与门禁.md](验证与门禁.md) §3）
7. 通过 → Phase 5

**本阶段硬要求**：
- 每个新增行为至少 1 条 L1 测试
- 改动 `Domain`/`Application` 必须跑 EditMode 全量
- 改动 `Presentation` 必须有 L4 截图
- 涉及存档结构变更 → 必须有 schema 往返测试（G7）

---

## Phase 5：知识沉淀与归档

1. 分析影响面，确定涉及的 `knowledge/{module}.md`
2. 调用 `/knowledge-set <module>` 更新知识库（默认 dry-run，确认后写）
3. 写 `06-knowledge-update.md`
4. 更新 `knowledge/README.md` 索引（如有新模块）
5. 确认 `07-spec-delta.md` 已产出（涉及行为变更时）→ 跑工具校验：
   `python tools/spec_tool.py validate --module {module}`。已有规格基线且本轮无行为变更时，校验与归档都加 `--no-delta`。
6. 归档（**工具执行，禁止手工合并**）：
   `python tools/spec_tool.py archive --module {module} --version {v} --subcategory {sub} --apply`
   → delta 合并进 `spec/{module}.md`；工具内部顺序为「校验 → 合并 spec → 移动文档 → 更新索引」，失败自动回滚
7. 回写工作计划（如有 `docs/WorkPlan_*.md`）

## 审核结果处理

| 结果 | 处理 |
|---|---|
| 通过 | 展示 → 用户确认 → 下一阶段 |
| 有条件通过 | 展示 → 用户决定是否修复 → 修复后重审或确认 |
| 不通过 | 展示 → 必须修复 → 重审 → 再确认（最多 3 轮） |

```
产物完成 → 调 reviewer → 写 04-review-report.md
    ↓
通过宿主提问工具展示摘要并等用户答复
    ↓
├─ 确认通过 → 追加确认记录 → 下一阶段
├─ 修复后重审 → 修复 → 重审 → 再问
└─ 讨论详情 → 澄清 → 更新报告 → 再问
```

## 自动 Hook（可选）

`.claude/settings.json` 可配置 `PostToolUse` 钩子，在写入 `01-requirements.md` / `02-design.md` 后自动触发 `plan-reviewer`，避免遗忘。
无 Hook 时，**在主会话里显式调用**——不因缺自动化而跳过审核。

---

## 与引擎无关的部分（迁移时不要改）

- 六阶段顺序与门禁三拍
- `04-review-report.md` 的追加式结构与"用户确认记录"段
- 严重度三级 + 修复轮次上限
- delta 的 ADDED/MODIFIED/REMOVED 语义与 validate 的 C1–C8（由 `spec_tool.py` 执行）
- `change/` → `spec/` → `knowledge/` 的三层职责划分
