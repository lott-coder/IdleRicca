## 需求审核

### 审核概要

- 审核类型为 requirements，审核对象为 `change/ui/_tmp/01-requirements.md`。
- 用户要求以 UGUI 实现血条、预留蓝条和 5 秒续连反馈，已确认由测试驱动 Ricca 受伤。
- 审核结果为有条件通过，阻断 0 项、警告 1 项、建议 2 项。
- 审核日期为 2026-11-22。

### 详细结果

#### 1. 需求覆盖与契约

- 血条、预留蓝条、续连窗口和受伤断连均有需求条目。有效命中沿用既有按挥击、按目标的判定，击杀计入与现有伤害结算相容。Application 的写权限、只读 HUD 和场景内数据生命周期明确。[gameplay 活规格 R5](../../../spec/gameplay.md#r5--剑身普攻和伤害)
- [info] 建议在 AC-5 拆分两种空挥场景。初始空挥后计数仍为 0。已有连击时空挥既保留当前计数，也让原计时继续流逝。当前「空挥为 0」容易被理解成空挥清零。
- [info] FR-1 和 AC-1 验收 HP 到 0 的显示。建议技术设计明确归零后角色能否继续挥击和建立新连击，以便保持玩家操控契约一致。

#### 2. 验收可执行性

- AC-1 至 AC-6 都列有可执行的证据级别。L1 可验证精确时间边界，L2 可通过受伤入口验证掉血和断连，L4 可验证布局。
- [warning] FR-4 要求倒计时刷新与命中强调，AC-6 只检查静态布局。建议补充连击 HUD 的 L2 或 L4 证据，覆盖倒计时在进入 2 连击时填满、等待时缩短、后续有效命中时回满且触发强调、超时时隐藏。该验收可通过测试时钟观察填充比例，再用录屏核对动效。

### 关键风险

| 等级 | 严重度 | 描述 | 影响 |
|---|---|---|---|
| P2 | warning | 连击倒计时与命中强调缺少具体的动态验收判据 | 只看静态截图可能漏掉倒计时失效、命中时未重置或强调未触发 |

### 执行建议

- 细化连击反馈验收后交用户确认需求。Phase 2 将确定配置、生命周期和 UI 状态，Phase 3 纳入 UI 验收证据。

## 设计审核

### 审核概要

- 审核类型为 design，审核对象为 `02-design.md` 与 `07-spec-delta.md`，对照已确认的 `01-requirements.md` 和 gameplay 在途契约。
- 审核结果为不通过，阻断 3 项、警告 2 项、建议 1 项。
- 审核日期为 2026-11-22。

### 详细结果

#### 1. 共享契约

- [blocking] **C1、C3、C5，Ricca HP 的写入口和配置归属待合并。** UI §2 规定 `IPlayerCommands.TryReceiveDamage(int)`、`PlayerCombatStatus` 和 `PlayerHealthSettings`。gameplay §2.2 由 `IEnemyCommands.TryHitRicca` 访问已绑定的 `PlayerActions` 并调用内部扣血入口，依赖只读 `CurrentHp`、`IsAlive`，另提出序列化初始 HP。须明确共用一个 HP 实例、一套生效配置和一处伤害结算，这处结算同时处理实际伤害与断连。测试与敌人命中入口都应委托给它。[UI 契约](02-design.md#2-数据结构) · [gameplay 契约](../../gameplay/_tmp/02-design.md#22-接口与状态)
- [blocking] **C5，Ricca 归零语义冲突。** UI 设计第 78 行规定归零后沿用移动和攻击。gameplay 设计第 120 行及 delta 的 R5、R9 规定归零原子取消在途挥击并拒绝移动和普攻。明确该行为引入的版本、两轮顺序，以及 HUD 如何消费该状态，再同步设计、验收和适用规格。[UI 交互流程](02-design.md#3-交互流程) · [gameplay R9](../../gameplay/_tmp/07-spec-delta.md)
- [blocking] **C4，Demo 场景和 Ricca 装配写入顺序待确定。** UI 接入 HUD 实例和 Ricca 生命配置，gameplay 写入相同场景的 EnemySpawner 与 Ricca 生命配置。独立副本各自修改后回写会有丢失场景引用或生命配置的风险。须明确写入顺序和最新基线，再验证场景中的 HUD 与生成器绑定同一个 Ricca，且保留既有场景引用。[UI 接入点](02-design.md#3-接入点) · [gameplay 接入点](../../gameplay/_tmp/02-design.md#3-接入点)

#### 2. 需求、生命周期和性能

- HP 和连击由 Application 裁定，UGUI 消费值类型快照。血条、满格 MP 占位、2 击显现、5 秒续连及动态反馈均有对应 L1、L2 或 L4 证据。存档、事件退订和输入阻拦的边界明确。
- [warning] UI delta R10 保证同帧显示扣血和断连，但 UI 设计目前只规定 HUD 晚于玩家的 `LateUpdate`。集成 gameplay 后，任何晚于 HUD 的受击生产端仍会让画面晚一帧。设计需明确所有相关战斗生产端与 HUD 的执行顺序，或把契约精确限定为下一次 HUD 绘制。用实际生产端顺序验证。[UI 执行顺序](02-design.md#4-性能与防御性设计) · [UI Δ R10](07-spec-delta.md)
- [warning] UI 设计隐藏未就绪数据，缺少绑定时给出诊断。应补齐配置资产存在但校验失败，以及角色暂时禁用后重新启用的明确状态和恢复行为。同步初始化可使用就绪、停用、显性失败三类结果，并以 L2 验证错误诊断及恢复，以满足 UI 验收的状态覆盖。[UI 绑定与防御](02-design.md#3-交互流程)
- [info] 预分配文本缓冲和按值刷新支持 0 B 稳态分配目标。进入执行计划时将目标落到 Profiler 取证，分别覆盖计时可见和数字强调期间，记录 Canvas 重建与 GC Alloc。[UI 验证与门禁 §9](../../../docs/rules/验证与门禁.md#9-ui-验收清单式双闸门)

### 关键风险

| 等级 | 严重度 | 描述 | 影响 |
|---|---|---|---|
| P0 | blocking | 两轮迭代尚未统一生命状态、受伤结算和归零行为 | 实战掉血、测试入口、连击和操控可能出现不同的结算结果 |

- Application 持有生命和连击。实体伤害走 gameplay 现有 `ReceiveEnemyDamage`，只有正伤害成功提交后才清空连击。出击沿现有判定和每挥击目标去重，只有有效扣血才计数，击杀同样计入。`PlayerActions.cs:80`、`PlayerActions.cs:140`。
